# PenTri v1.20 요구사항 정리

작성 기준: 2026-09-10 사용자 대화와 사용자가 제공한 「PenTri DCB」 기록.
코드 기준: `pentri-v1.10-patched.zip` (`version: 1.1.0`, `version_name: v1.10`).

이 문서는 요구사항 초안이다. 사용자 요구, 코드 관찰, 제안을 구분한다. 스토어 v1.00 소스와의 비교는 수행하지 않았으며, 아래 항목은 구현 완료를 뜻하지 않는다. DCB 명칭의 확장 의미나 제품명 변경은 정해지지 않았다.

## 1. 제품 방향과 작업 범위

사용자 방향: 웹 취약점 진단을 보조하며 **정찰 → 분석 → 기록**을 지원한다.

| 구분 | 범위 |
| --- | --- |
| 1. 기능 개선 | 기존 진단·수집 정확도, 상태 유지, 화면 구성, 실행 오류 개선 |
| 2. 기능 추가 | CVE 검색과 보고서 연결, 자주 쓰는 문구, 증적 캡처·간단한 편집 |
| 3. GitHub 저장소 정리 | v1.20 소스 구조, 문서, 의존성·라이선스 고지, 검증·릴리스 정리 |
| 4. Chrome 웹 스토어 업데이트 | 최종 구현에 맞는 설명·화면·권한·개인정보처리방침과 배포 패키지 |

- v1.20의 실행 형태: Chrome 확장 아이콘 클릭 시 별도 도구 창을 연다.
- 장기 구상: 별도 실행 프로그램(exe). v1.20의 확정 구현 범위에 포함하지 않는다.
- 표시 버전은 v1.20으로 계획한다. manifest 내부 숫자 버전은 배포 준비 시 기존 스토어 패키지와 함께 확정한다.

## 2. 화면 구성

확정 방향: 상위 탭을 **Recon / Analyze / Report / Tools**로 개편한다. 상위 탭과 하위 탭은 크기·간격·강조 방식으로 명확하게 구별한다.

다음 하위 배치는 제안이며, Analyze의 세부 구성은 아직 확정하지 않았다.

| 상위 탭 | 하위 기능 배치안 | 역할 |
| --- | --- | --- |
| Recon | Tech Stack, Endpoints(External 통합), Robots, Source Map, Comments, Path Scan | 점검 대상과 단서 수집 |
| Analyze | 점검 후보 검토, CVE 검색·대상 연계 | 근거를 보고 실제 점검할 내용을 판단 |
| Report | 진단 기록, 증적 캡처·편집, 보고서 내보내기 | 발견 사항과 증적을 연결해 기록 |
| Tools | Cipher, CheatSheet, 문구함 | 반복 작업과 수동 진단 보조 |

별도 창 전환의 구현 전제:

- 도구를 연 웹 탭을 명시적인 대상 탭으로 보관하고 대상 URL을 계속 표시한다.
- 창에 포커스가 있어도 조회·스캔·캡처가 같은 대상에 연결되도록 한다.
- 대상 탭 변경·페이지 이동·탭 닫힘 시 결과 처리 기준을 둔다. 이전 페이지 결과를 현재 페이지 결과로 표시하지 않는다.
- 화면 수명과 작업·결과 수명을 분리한다. 창을 다시 열면 해당 대상의 보관된 결과를 복원한다.
- 여러 창 허용 여부, 창 위치·크기 복원, 진행 중 작업의 창 닫힘 동작은 세부 설계 항목이다.

## 3. 기존 기능 변경 목록

| 기능 | 사용자 요구 | 코드 관찰 및 개선 방향 |
| --- | --- | --- |
| Tech Stack | Wappalyzer를 더 참고하여 정확도 향상 | 현재 DB를 읽는 코드에 미지원 필드·불완전한 패턴 해석이 있음. 탐지 근거, 버전 추출, 중복 병합을 함께 개선. DB를 가져올 경우 출처·라이선스 확인 |
| Endpoints + External | 하나로 통합 | URL 목록에 내부/외부, 도메인, 출처, 리소스 종류, API 여부를 필터로 제공하는 안. URL origin의 정확한 비교 필요 |
| Robots | 기존 기능 유지 | 화면·기능 재설계 요청은 없음. 공통 대상 관리·오류 처리 변경은 적용 |
| Source Map | 존재 확인 결과 유지 | 후보뿐 아니라 판정 상태·확인 시각·실패 이유를 보관. 미확인, 노출, 접근 제한, 확인 실패를 구별. 보존 기간은 별도 결정 |
| Comments | 상세 파싱, HTML 주석, 파일·경로 출처 확인 | DOM HTML 주석 수집은 이미 구현되어 있음. 현재 상한 60개, 항목당 300자이며 출처를 DOM으로 표시. 외부 JS는 정규식으로 추출하고 파일명만 저장. 전체 URL·주석 유형·문맥을 보존하고 줄 위치는 정확히 산출 가능한 소스에 표시 |
| Path Scan | 디렉터리 목록 재점검 | 현재 7개 분류: 관리 콘솔, 개발 도구/API 문서, 설정 파일, 백업/임시 파일, VCS/소스코드, 인증/세션, 업로드/파일. 중복·효용·부하·상태 변경 가능성을 검토하고 실행 전 선택 경로를 보여주는 안 |
| JS Analyze | Analyze 전체 재설계 | 기존 정규식 결과 나열의 실무 효용이 낮다는 사용자 피드백 반영. 규칙별 근거·위치·후속 확인·보고서 연결 중심으로 재설계 검토 |
| Upload | 기존 방식 재검토 | accept·enctype 등 DOM 단서만으로 서버 업로드 취약성을 판정하지 않음. 독립 탭 유지 여부는 미정이며 유용한 폼·업로드 메타데이터의 재사용은 검토 |
| Cipher | 변환 결과 유지, Clear, 가능하면 단기 history | 현재 화면 메모리 위주. 입력·변환 종류·출력·시각을 기록하는 안. 화면 Clear와 기록 전체 삭제를 구별하고 보존 기간·개수 제한은 별도 결정. MD5 오류 수정 선행 |
| CheatSheet | 세부 페이로드 정비, Settings 제거, 공격자 링크를 test.com으로 통일 | CheatSheet 내부 Settings 제거 요구로 해석. 예제의 호스트 표기와 사용자 설정 치환 코드를 함께 점검. 다른 실제 출처·참고 링크까지 일괄 치환하지 않음 |
| Diag Texts | CheatSheet에서 분리 | 새 문구함으로 통합하는 배치안. 사용자 템플릿과 보고서의 개별 진단 기록은 역할을 구분 |

주석 수집의 검증 범위에는 HTML DOM에 남은 주석, 동적으로 추가·제거된 주석, 인라인 JS, 외부 JS, 같은 파일명의 서로 다른 URL을 포함한다. DOM에서 얻은 주석의 위치를 원본 HTML 줄 번호로 추측해 표시하지 않는다. HTML 주석의 표준 표기는 `<!-- ... -->`이다.

Path Scan 목록에는 `/logout`, `/actuator/heapdump` 등이 포함되어 있다. 요청 의미·부하가 서로 다르므로 목록 정비 시 기본 선택 여부를 따로 검토한다.

## 4. 추가 기능

### CVE 검색과 리포트

사용자 요구: CVE 검색 및 리포트 기능.

- 현재 Tech Stack의 NVD 키워드 조회를 독립 검색과 결과 선택·저장·보고서 연결로 확장하는 안.
- 검색 결과 자체와 해당 대상에 대한 영향 판단을 구별한다.
- 보고서에 포함할 검색 결과, 제품·버전 근거, 사용자의 판단·메모를 연결하는 안.
- 현재 기술 키워드 조회와 어떤 UX로 통합할지 세부 설계한다.

### 자주 쓰는 문구함

사용자 요구: 진단 안내, 점검 시작, 민감한 점검 시작 등의 문구를 빠르게 복사.

- 기존 Diag Texts의 편집·저장 기능을 활용할 수 있다.
- 문구 분류·검색·복사 제공을 제안한다. 즐겨찾기와 변수 치환은 선택적 후속 항목이다.
- 이 요구는 사용자가 선택한 문구를 클립보드로 복사하는 기능이며, 메시지 자동 발송 요구가 아니다.

### 증적 캡처와 편집

사용자 요구: 스크린 캡처, 크기 자동 조절, URL 기록, 간단한 도형 편집.

- 대상 URL·캡처 시각과 이미지를 묶어 진단 기록에 연결하는 안.
- 크기 조절의 의미는 출력용 리사이즈, 캡처 영역 자동 선택 중 추가 정의가 필요하다.
- 캡처 범위(보이는 영역/선택 영역/전체 페이지), 도형 종류, 저장 형식은 미정이다.
- 원본과 편집 결과 보관, 삭제·보관 정책, 보고서 이미지 출력은 함께 설계한다.
- 사용자 피드백을 받은 뒤 범위를 정할 수 있도록 첫 구현 단위를 작게 나눈다.

## 5. Analyze 재설계 제안

이 절은 사용자 확정 요구가 아닌 검토안이다.

사용 흐름: **점검 후보 선택 → 근거·출처 확인 → 수동 점검 내용 기록 → Report에 추가**.

- 민감정보·코드 단서를 전체 URL, 가능한 줄 위치, 코드 문맥과 함께 보여준다.
- 입력 필드·폼·업로드 메타데이터를 수동 점검에 필요한 정보로 제공한다.
- 사용 함수·문자열이 존재한다는 사실과 취약성의 확정 여부를 구별한다.
- 필터링 분석은 발견한 정규식·필터 로직의 설명과 로컬 예제 비교를 후보로 둔다.
- 불필요한 규칙은 삭제하고 유용한 수집 코드의 재사용 여부는 재설계 과정에서 결정한다.

## 6. 추가 검토 후보

사용자 기록의 물음표·고려 항목을 그대로 후속 후보로 보관한다. v1.20 확정 기능으로 편입하지 않는다.

- 통제된 진단 환경에서 사용할 테스트 서버 연계: 용도, 운영 주체, 기록 범위부터 정의.
- XSS 필터링 분석: 입력·변환·출력 문맥 비교 등 필요한 사용 시나리오 정의.
- 정규식 분석: 테스트 문자열, 매칭 구간, 캡처 그룹, 치환 결과를 로컬에서 확인하는 도구 검토.
- 별도 exe: 확장 기능 안정화 후 실행 환경과 공유 가능한 분석·보고서 로직을 검토.

## 7. 선행 코드 개선과 검증 기준

기존 리뷰의 수정 필요 항목을 UI 개편·기능 추가와 함께 추적한다.

| 묶음 | 개선 항목 | 검증 기준 예시 |
| --- | --- | --- |
| 실행 정확성 | 스크립트 중복 주입, 스캔 완료 동기화, MD5 | 같은 페이지에서 연속 재스캔 성공, 최종 결과 일치, 표준 해시 벡터 일치 |
| 대상·상태 | 탭·문서·실행 식별, 스캔 중지/재시작, 결과 저장 | A/B 탭 전환·페이지 이동·창 재개방에서도 결과 혼합 없음 |
| 네트워크 | origin 비교, 응답 크기 제한, 경로 오탐, 소스맵 URL·판정 | 유사 도메인 구별, 초과 응답 중단, 공통 200 오류 페이지·쿼리 포함 JS 검증 |
| 데이터·보고서 | 민감정보 마스킹, 출처 보존, JSON/HTML 항목 일치 | 선택된 진단 항목·증적·CVE가 내보내기에 반영되고 마스킹 정책 일치 |
| 유지보수 | popup 기능 분리, 공통 결과 모델, 의존성 고지 | 기능별 책임이 구분되고 수정 대상에 맞는 검증 가능 |

기존 DevTools 진입점 유지 여부는 별도 창 설계에서 결정한다. 유지할 경우 초기화 스크립트와 검사 대상 탭 연결을 수정한다.

## 8. GitHub와 스토어 준비에 연결할 사항

- 2026-09-11 사용자 확정 방향: 기존 `https://github.com/O-SQZ/pentri` 저장소를 계속 사용하며, 개인정보처리방침 중심 저장소를 v1.20 제품 소스·문서·릴리스 저장소로 확장한다. 로컬 origin이 해당 주소로 설정된 것을 확인했다. 원격 쓰기 권한은 아직 확인하지 않았다.
- 저장소 이름은 미정이다. 사용자 후보는 `PenTri` 또는 더 긴 이름이며, 제안 후보는 `pentri-toolkit`이다. 이름에 버전은 넣지 않고 릴리스 태그로 관리하는 안을 제안한다.
- 저장소 이름 변경 시 기존 스토어 개인정보처리방침 링크를 함께 점검한다. GitHub 저장소 리다이렉트와 GitHub Pages 프로젝트 사이트 URL은 다르며, 프로젝트 사이트 URL은 자동 리다이렉트 대상에서 제외된다. 근거: [GitHub 저장소 이름 변경 문서](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository).
- 이름 확정 후 로컬 origin, Pages 주소, 저장소 문서 링크, 스토어 개인정보처리방침 URL을 함께 갱신하고 접근 여부를 검증한다. 현재 이름 변경이나 원격 게시를 수행한 상태는 아니다.
- 첨부 ZIP에는 저장소 문서가 없지만 현재 작업 저장소의 `docs/README.md`와 `docs/privacy/index.html`은 존재한다. 후자는 v1.00 표기이므로 배포 단계에서 최종 데이터 처리와 대조해 갱신한다.
- 소스 구조, 설치·사용법, 기능 한계, 버전 변경 내역, 테스트 방법, 제3자 코드·DB·아이콘 출처를 정리한다.
- 소스맵 결과, 변환 기록, 진단 메모, 캡처 이미지의 저장 범위·기간·삭제 방식을 구현과 문서에 동일하게 반영한다.
- GitHub 게시와 스토어 업데이트는 기능 범위·검증·배포 자료를 갖춘 뒤 진행한다. 이 문서 작성은 업로드나 배포를 실행하지 않는다.

## 9. 다음 설계에서 정할 항목
